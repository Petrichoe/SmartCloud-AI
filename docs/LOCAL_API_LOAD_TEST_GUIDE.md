# 本地接口压测通用流程与记录

本文沉淀本项目在本地执行接口压测的通用流程，适用于优惠券、课程、用户、交易等不同业务接口。流程覆盖接口识别、环境检查、合成数据准备、JMeter 测试计划、分阶段执行、指标统计、结果判断和临时数据清理。

> 本流程默认针对测试环境或本机服务。涉及生产环境、真实用户数据、真实订单或不可逆写操作时，必须先确认范围、数据和回滚方案。

## 1. 通用执行原则

以后收到任意接口压测请求，按以下顺序执行，不把某个业务的表结构、请求体或认证方式硬编码成通用规则：

1. 先从 Controller、DTO、Service 和配置中确认真实的请求方法、路径、参数、认证头、成功响应和依赖服务。
2. 优先使用合成数据和隔离测试用户；需要数据库夹具时使用唯一 `runTag`，并记录本轮创建的 ID。
3. 先执行单请求冒烟，再执行低并发基线，最后执行短压或逐级加压。
4. 默认只调用查询或计算接口；写接口只有在明确授权、幂等、可回滚且清理方案已确认时才允许压测。
5. 压测结束后必须精确清理临时数据和结果文件，并复核数据计数。
6. 汇报时区分“本机短压结果”“网关完整链路结果”和“优化前后对比结果”，不能把一次短压直接表述成容量结论。

## 2. 接口识别与前置检查

### 2.1 需要确认的信息

| 项目 | 需要确认的内容 |
| --- | --- |
| 请求定义 | HTTP 方法、路径、Query、Path、Header、Cookie、Body |
| 身份认证 | 直连所需的内部身份头，或网关所需的有效 JWT |
| 成功标准 | HTTP 状态码、业务状态码、必需响应字段、响应断言 |
| 代码入口 | Controller、Service，以及是否包含 Feign、MQ、Redis 或数据库访问 |
| 依赖状态 | 目标服务端口、注册中心、缓存、消息队列、数据库和下游服务 |
| 测试数据 | 是否需要用户、商品、课程、订单或其他业务夹具 |
| 风险边界 | 是否会扣库存、发券、扣款、发消息或修改真实业务状态 |

### 2.2 选择调用入口

优先直连目标服务，隔离网关认证和路由开销：

```text
http://<service-host>:<service-port>/<service-path>
```

如果需要评估用户实际访问链路，再使用网关地址：

```text
http://<gateway-host>:<gateway-port>/<gateway-route>
```

直连和网关是两种不同的测试口径，结果不能混在一起比较。网关链路必须使用真实有效的认证信息；禁止用无效 token 得到 401/403 后仍把结果当作接口性能。

在当前工作区，JMeter 批处理程序默认位于：

```powershell
$JMeter = 'D:\software\develop software\apache-jmeter-5.6.3\bin\jmeter.bat'
```

涉及 VMware、Docker、Nginx、网关或远程服务时，先阅读 [VMware 本地访问约定](VMWARE_LOCAL_ACCESS.md)，再做实时检查。

## 3. 合成数据与夹具隔离

### 3.1 通用夹具流程

当接口依赖数据库中的业务数据时：

1. 生成唯一 `runTag`，例如 `CODEX_PERF_<时间>_<随机串>`。
2. 创建只属于本轮测试的用户、资源和关联记录，禁止使用真实用户或线上数据。
3. 使用事务提交夹具，并记录主表 ID、关联表 ID、测试用户 ID 和 `runTag`。
4. 用真实业务请求体执行一次冒烟，确认数据确实能被接口读取并产生预期业务结果。
5. 测试完成后按外键依赖的逆序删除：子表、关联表、主表。
6. 删除后复核本轮 `runTag`、测试用户和所有已记录 ID 的残留计数均为 0。

能通过官方测试 API 创建且能可靠回收的数据，优先走官方 API；只有在 API 会引入额外异步链路、缓存状态或难以回滚时，才在获得授权并确认表结构后直接写入隔离测试库。

### 3.2 数据安全边界

- 数据库凭据只能从现有受控配置注入当前进程，不能写入 SQL、JMX、脚本、日志或命令行参数。
- 夹具名称、业务编码和测试用户 ID 必须能唯一识别本轮数据。
- 不使用无条件全表删除、重置自增、清空 Redis 或重启服务代替精确清理。
- 如果目标接口会产生 MQ 消息、Redis 键、文件或外部副作用，清理清单必须同时覆盖这些资源。
- 清理脚本执行前先查询匹配数量；数量不符合预期时停止，不继续删除。

## 4. JMeter 测试计划

### 4.1 最小组件

通用 JMX 测试计划至少包含：

- HTTP Request Defaults：协议、目标服务器和端口；
- HTTP Request：目标方法、路径、Query 和 Body；
- HTTP Header Manager：Content-Type、Accept、身份头和业务必需头；
- 参数化变量：测试用户、`runTag`、环境地址和业务参数；
- Response Assertion：HTTP 状态和业务成功标记；
- Thread Group：线程数、爬升时间和持续时间可通过 JMeter 属性传入；
- 结果配置：非 GUI 运行，不保存响应体，避免结果文件泄露数据并无谓膨胀。

请求头中的 JMeter 变量使用类似 `user-info: ${userId}` 的形式；具体变量名必须与 JMX 和启动命令保持一致。JMX 文件只保存占位符，不保存真实身份信息、JWT、数据库凭据或生产地址。

### 4.2 成功断言

只判断 HTTP 200 不够。根据目标接口选择至少一个稳定的业务断言，例如：

- JSON 中存在非空业务结果字段；
- 业务状态码为成功值；
- 返回数组长度大于 0；
- 关键金额、状态或 ID 字段满足预期；
- 错误响应中不能出现业务失败码。

如果接口允许合法空结果，应把“空结果”和“请求失败”区分开，并在报告中说明断言规则。

## 5. 分阶段执行

### 5.1 冒烟请求

先使用 1 个请求确认：

- 服务可访问；
- 认证有效；
- 请求体格式正确；
- 合成数据已生效；
- HTTP 状态和业务断言均通过。

冒烟失败时不进入并发压测，先修正接口、夹具或环境问题。

### 5.2 基线和短压

默认可以先使用 1 并发、10 秒基线，再使用 5 并发、5 秒爬升、30 秒短压。它们是低风险起始参数，不是所有接口的固定标准；需要根据接口是否读写数据库、是否触发下游调用和是否存在外部副作用调整。

```powershell
& $JMeter -n -t '.\api-load-test.jmx' -Jthreads=1 -JrampUp=1 -Jduration=10 -l '.\api-load-test-baseline.jtl' -j '.\api-load-test-baseline.log'
```

```powershell
& $JMeter -n -t '.\api-load-test.jmx' -Jthreads=5 -JrampUp=5 -Jduration=30 -l '.\api-load-test-short.jtl' -j '.\api-load-test-short.log'
```

`api-load-test.jmx`、JTL 和日志都是临时产物。结果统计完成后删除，或只保留脱敏后的汇总指标。

如果接口需要测试用户、租户或其他上下文参数，再按 JMX 中的变量名追加对应的 `-J参数名=参数值`；例如优惠券案例使用 `-JuserId=$testUserId`。

### 5.3 逐级加压

如果短压通过，再按目标逐级增加并发，例如 1、5、10、20、50。每一级都要观察：

- 错误率和错误类型；
- P95/P99 是否突增；
- 线程池、数据库连接池、CPU、内存和 GC；
- Redis、MQ、Feign 下游和网关是否出现瓶颈；
- 是否产生未清理的业务副作用。

对于写接口，先做低并发幂等验证，再决定是否允许并发；不把“能发请求”当作“可以安全压测”。

## 6. 结果统计口径

从 JTL 的 `elapsed` 和 `success` 字段统计：

- 样本数、成功数、错误数和错误率；
- 吞吐量；
- 平均值、最小值、最大值和标准差；
- P50、P90、P95、P99、P99.9；
- 必要时按响应码、断言、线程组或请求标签拆分。

成功定义必须同时满足 HTTP/业务断言。吞吐量优先从同一份 JTL 统一统计；JMeter 控制台显示值可能因统计时间边界略有差异。

建议报告使用以下表格：

| 场景 | 并发 | 爬升 | 持续时间 | 样本数 | 成功率 | 平均 | P95 | P99 | 最大 | 吞吐量 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 基线 |  |  |  |  |  |  |  |  |  |  |
| 短压 |  |  |  |  |  |  |  |  |  |  |

单次本机短压不能证明生产容量，也不能单独证明“从 800 ms 优化到 100 ms 以内”。优化前后比较必须固定：

- 代码版本；
- 测试数据；
- 机器和依赖环境；
- 并发模型；
- JMeter 计划；
- 统计口径。

## 7. 清理临时数据

清理脚本不能假设所有业务都有相同表名，应根据实际夹具建立“子表到主表”的逆序清理清单。通用结构如下，尖括号内容必须替换为实际表和字段：

```sql
-- 先确认本轮标记只匹配测试数据
SELECT COUNT(*) AS matched_rows
FROM <parent_table>
WHERE <run_tag_column> = '<RUN_TAG>';

START TRANSACTION;

-- 先删除依赖主表的子表或关联表
DELETE FROM <child_table>
WHERE <foreign_key> IN (
    SELECT <id_column>
    FROM <parent_table>
    WHERE <run_tag_column> = '<RUN_TAG>'
);

-- 再删除主表
DELETE FROM <parent_table>
WHERE <run_tag_column> = '<RUN_TAG>';

COMMIT;

-- 使用已记录的 ID 或同样的唯一标记复核残留
SELECT COUNT(*) AS remaining_parent
FROM <parent_table>
WHERE <run_tag_column> = '<RUN_TAG>';

SELECT COUNT(*) AS remaining_child
FROM <child_table>
WHERE <foreign_key> IN (<RECORDED_ID_LIST>);
```

如果业务数据没有 `runTag` 字段，就使用本轮记录的精确 ID 列表或隔离测试用户 ID；不要用模糊条件清理真实数据。创建、冒烟或压测中途失败时，也必须执行同一轮清理并复核。

## 8. 汇报模板

每次压测完成后，按以下结构汇报：

1. 测试目标和实际调用入口；
2. 测试环境、代码版本和是否经过网关；
3. 合成数据范围、并发模型和持续时间；
4. 样本数、成功率、平均、P95、P99、最大值和吞吐量；
5. 错误类型及资源瓶颈（如有）；
6. 是否达到本次约定的响应目标；
7. 临时数据和临时文件是否已清理；
8. 结果限制，以及是否需要继续做逐级加压或优化前后对比。

## 9. 本次优惠券组合计算验证案例

本节只是通用流程的一次业务示例，后续测试其他接口时替换本节内容，不改变前面的执行框架。

### 9.1 接口和夹具

- 主接口：`POST /user-coupons/available`；
- 代码入口：`DiscountServiceImpl#findDiscountSolution`；
- 直连地址：`http://127.0.0.1:8092/user-coupons/available`；
- 临时夹具：5 张券、5 条 `user_coupon`、3 条 `coupon_scope`；
- 合成课程：4 门课程，覆盖分类 101、102、103；
- JMeter 断言：HTTP 200 且响应包含 `discountAmount`。

使用的券规则覆盖全场满减、全场折扣、分类满减、分类每满减和分类无门槛，金额单位为分：

| 后缀 | `discount_type` | `specific` | `discount_value` | `threshold_amount` | `max_discount_amount` | 范围 |
| --- | ---: | --- | ---: | ---: | ---: | --- |
| A | 4（满减） | 0 | 5000 | 60000 | 0 | 全部 |
| B | 2（折扣） | 0 | 85 | 50000 | 9000 | 全部 |
| C | 4（满减） | 1 | 5000 | 30000 | 0 | 分类 101 |
| D | 1（每满减） | 1 | 1000 | 10000 | 3000 | 分类 102 |
| E | 3（无门槛） | 1 | 2000 | 0 | 0 | 分类 103 |

合成课程请求体：

```json
[
  {"id": 910000001, "cateId": 101, "price": 20000},
  {"id": 910000002, "cateId": 102, "price": 18000},
  {"id": 910000003, "cateId": 103, "price": 22000},
  {"id": 910000004, "cateId": 101, "price": 15000}
]
```

### 9.2 实际短压结果

| 场景 | 并发 | 持续时间 | 样本数 | 成功数 | 错误数 | 平均 | P95 | P99 | 最大 | 标准差 | 吞吐量 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 并发基线 | 1 | 10 秒 | 871 | 871 | 0 | 11.06 ms | 19 ms | 29 ms | 64 ms | 4.38 ms | 87.96 req/s |
| 5 并发短压 | 5 | 30 秒 | 12,667 | 12,667 | 0 | 10.88 ms | 16 ms | 30 ms | 82 ms | 3.84 ms | 423.33 req/s |

所有请求均返回 HTTP 200，断言全部通过。临时券、用户券和范围记录清理计数均为 0，JMX、JTL 和日志临时文件已删除。

该结果是当前代码、当前本机环境和小规模合成夹具下的短压结果，不包含网关完整链路，也不代表生产容量。

## 10. 视频播放进度高并发写入验证案例

本节是通用流程在“高频视频心跳写入”场景中的一次实际验证，后续其他写入型接口仍沿用前面的夹具隔离、冒烟、基线、短压、异步结果核对和清理流程。

### 10.1 接口和测试数据

- 实际入口：`POST /learning-records`；
- 服务：`learning-service`，本机端口 8090；
- 请求头：`user-info` 携带合成测试用户 ID；
- 请求体：视频类型（`sectionType=1`）、合成 `lessonId`、合成 `sectionId`、`duration=600`、`moment=20`；
- 临时夹具：1 条合成 `learning_lesson` 和 1 条未完成的 `learning_record`；
- 设计目的：让心跳命中已有学习记录，进入 Redis 缓存和延迟队列路径，避免把“首次创建记录”的一次数据库写入混入心跳压测。

### 10.2 实际短压结果

| 场景 | 并发 | 持续时间 | 样本数 | 成功数 | 错误数 | 平均 | P95 | P99 | P99.9 | 最大 | 吞吐量 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 并发基线 | 1 | 10 秒 | 1,274 | 1,274 | 0 | 7.55 ms | 11 ms | 30 ms | 42 ms | 50 ms | 128.51 req/s |
| 5 并发短压 | 5 | 30 秒 | 16,451 | 16,451 | 0 | 8.40 ms | 11 ms | 32 ms | 42 ms | 54 ms | 549.98 req/s |

所有请求均返回 HTTP 200。等待延迟窗口后，数据库中的合成记录核对为 `moment=20`、`finished=0`，课表的最近学习小节已更新，说明异步写回链路实际执行成功。MySQL 临时记录、Redis 缓存键和 JMeter 结果文件均已清理。

### 10.3 与目标描述的差异和限制

当前仓库实现的实际链路是“Redis Hash + JVM 进程内 `DelayQueue`（延迟 20 秒）+ 异步合并写 MySQL”，不是严格意义上的 Redis 分布式延迟队列。当前代码中的 `@PreDestroy` 只停止处理循环，没有把队列中的未处理任务排空；多实例部署、强制重启和单节点故障仍需单独评估。

本次 1/5 并发短压只验证了请求可用性和异步写回，不足以证明“数据库负载降低 90%”或“彻底消除雪崩风险”。要验证这些结论，还需要记录压测期间实际数据库 UPDATE 次数、连接池/线程池、Redis 延迟、队列积压、服务资源，以及优化前版本的同口径对照结果。
